# Politique de sécurité

_English version below._

## Versions prises en charge

Seule la dernière version publiée reçoit les correctifs de sécurité. Tant que le numéro de version est en `0.y.z`, aucune correction n'est faite sur une version plus ancienne : le correctif sort dans une nouvelle version, qui s'installe par une mise à jour.

## Signaler une faille

Signalez une faille en privé, par le signalement privé de vulnérabilités de GitHub : le bouton « Report a vulnerability » de l'onglet « Security » du dépôt, ou directement cette adresse :

<https://github.com/torsade-project/torsade/security/advisories/new>

Ne signalez jamais une faille dans un ticket, une discussion ou une pull request publics : tout le monde pourrait la lire avant qu'elle soit corrigée. Aucune adresse mail n'est donnée pour les signalements.

## Ce qu'il faut indiquer

- La version de Torsade concernée.
- La description de la faille.
- Les étapes pour la reproduire.
- Son impact : ce qu'un attaquant peut lire ou faire, et avec quel accès.

N'y mettez aucune donnée réelle d'une organisation, ni plan d'adressage, ni nom, ni adresse : décrivez la faille avec des données fictives, celles de la démonstration par exemple.

## La suite

1. Un accusé de réception.
2. Un correctif, publié dans une nouvelle version, avec un avis de sécurité sur GitHub.
3. La mention de la personne qui a signalé la faille dans cet avis, si elle le souhaite.

Aucun délai n'est garanti : le projet a un seul mainteneur, bénévole.

# Security policy

## Supported versions

Only the latest published release receives security fixes. While the version number is `0.y.z`, no fix is made to an older version: the fix comes in a new release, installed by an update.

## Reporting a vulnerability

Report a vulnerability privately, through the private vulnerability reporting of GitHub: the "Report a vulnerability" button of the "Security" tab of the repository, or directly this address:

<https://github.com/torsade-project/torsade/security/advisories/new>

Never report a vulnerability in a public issue, discussion or pull request: anyone could read it before it is fixed. No email address is given for reports.

## What to include

- The version of Torsade.
- A description of the vulnerability.
- The steps to reproduce it.
- Its impact: what an attacker can read or do, and with which access.

Do not include any real data of an organisation, no addressing plan, name or address: describe the vulnerability with made-up data, such as those of the demonstration.

## What happens next

1. An acknowledgement of receipt.
2. A fix, released in a new version, with a security advisory published on GitHub.
3. Credit in that advisory for the person who reported the vulnerability, if they wish.

No timeline is guaranteed: the project has a single maintainer, a volunteer.
